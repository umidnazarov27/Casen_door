## 1. Target stack

| Layer | Planned choice | Responsibility |
|---|---|---|
| Storefront placement | Shopify page template + custom Liquid section | Mount on `/pages/kitchen-configurator` within the existing theme |
| Interface | React + TypeScript + Vite | Four steps, state, options, gallery, summary and quotation controls |
| Styling | CSS Modules plus a scoped component root | Match the design while avoiding global resets or changes to unrelated pages |
| Shared logic | Plain TypeScript modules | Catalogue types, runtime validation, compatibility, money/VAT and photo resolution |
| Catalogue/media | Shopify Metaobjects and Files/media | Staff-maintained content and photographs |
| Storefront/backend bridge | Shopify app proxy | Same-store URL for catalogue and quotation requests |
| Backend | Node.js + TypeScript on Vercel Functions | Trusted catalogue access, validation, quotation orchestration and email |
| PDF | `@react-pdf/renderer` on the server | Branded document with resolved options, imagery, totals and notices |
| Email | Resend adapter | Customer-confirmed PDF attachment dispatch |
| Quote state | Small managed PostgreSQL database | Immutable quote snapshots, request deduplication and dispatch state |
| PDF files | Private object storage; default candidate Vercel Blob | Store generated bytes independently of function invocations |
| Verification | Vitest, React Testing Library, Playwright + manual device/PDF checks | Behaviour, integration and real customer journeys |

PostgreSQL provider, storage plan, service owners and costs are audit decisions before provisioning. Reuse suitable existing services where doing so reduces maintenance. Package versions and Node version are selected from mutually supported current releases during setup and locked in the repository. These are proposed dependencies, not installed tools.

Use React's reducer/context for this four-step state initially; a global state library is unnecessary unless implementation exposes a concrete need. The storefront does not require Next.js, a full headless rebuild or an iframe. React builds to assets loaded by the Liquid section. Shopify supplies the surrounding page.

Shopify supports page templates composed of sections; Vite supports integration with externally rendered HTML. Build the theme asset loader and bundle output together, including all referenced chunks/assets. [Shopify templates](https://shopify.dev/docs/storefronts/themes/architecture/templates/json-templates), [Vite backend integration](https://vite.dev/guide/backend-integration).

## 3. Shopify setup and release boundary

1. Inspect the actual store, theme, templates, apps, existing custom code and reference design. Verify that the intended page template can be assigned and that a full-width section fits the theme.
2. Identify the app owner and installation model for this client store. Create/configure the single-store integration using the supported Shopify flow; choose Admin API authentication for that ownership model and store credentials only on the server.
3. Do not assume the client-credentials grant is available simply because the app serves one store: Shopify documents it for apps/stores in the same organization. Verify ownership; use the supported authorization flow for a client-owned store when needed. [Shopify authentication guidance](https://shopify.dev/docs/apps/build/authentication-authorization/client-credentials-grant?lang=node).
4. Request only necessary access, including app proxy configuration and catalogue/media reads or setup writes as justified. Record the selected API version and permission list.
5. Create the custom section with a React mount point, theme settings for copy/integration path and the compiled asset loader. Initialize/unmount safely when the theme editor adds or reloads a section.
6. Assign the dedicated template to the intended page in a preview/development environment. Load configurator assets only where its section is present; preserve the theme header/footer.
7. Configure a proxy root such as `/apps/casen-configurator` to the backend. Treat this path as configuration because merchants can customize proxy paths.
8. Verify proxy signatures and target shop on all applicable backend requests. Signature verification proves forwarding by Shopify, not customer identity or permission to view a private quote. Use separate scoped quote tokens and validate every request body. [Proxy authentication](https://shopify.dev/docs/apps/build/online-store/app-proxies/authenticate-app-proxies).
9. Keep staging separate. An unpublished theme alone does not isolate a store's app proxy/backend configuration. Prefer a development store/test app and staging services; document any shared-store preview constraints before using that route.

Before live changes, preserve the relevant theme files/settings and deploy only the configurator changes. Record theme release, frontend asset version, backend release and database migration version together. Avoid destructive schema changes; rollback must preserve issued quotation records.

## 4. Catalogue contract and publishing

Create merchant-editable definitions for layout, island, storage, carcass, combination-photo mappings and catalogue/pricing settings. Use stable IDs and referenced records instead of hardcoded UI option lists. The detailed required fields remain in [ARCHITECTURE.md](ARCHITECTURE.md).

- The server reads authoritative records through the selected Shopify API adapter. It returns only public catalogue fields to the storefront; Admin API credentials never enter Liquid or the browser bundle.
- Fetch all pages of catalogue data and normalize it into the same domain schema used by fixtures. Validate types, active references, dimensions, prices, currency and compatibility before using it.
- Use a catalogue revision derived from normalized content, plus a controlled publication process. Do not let a partial import become a launch catalogue; validate the full candidate before activating it.
- Share the domain calculation/rule code between browser and server. The browser gives immediate estimates; the server independently resolves IDs and calculates the issued quotation.
- Start with a short, documented catalogue cache and a deliberate refresh mechanism after staff edits. Before issuing a quote, check the authoritative revision; if changed, return revised data for customer review. Avoid silently issuing a new total.
- Demonstrate staff edits and new records without rebuilding JS. Document when changes become visible and how to diagnose validation errors.
- Enumerate valid combinations, not just every raw Cartesian product. Produce missing-photo and inaccessible-asset reports, then have Casen Doors verify that each image depicts the combination correctly.

## 5. Backend contracts and persistence

The following are planned paths beneath the configured proxy root. Final routing names can change during the week-one spike without changing product scope.

| Method and path | Contract | Main failure handling |
|---|---|---|
| `GET /catalogue` | Return validated public catalogue plus revision | Unavailable/invalid catalogue gets a retry state, never invented prices |
| `POST /quotes` | Selected IDs, catalogue revision and idempotency key; return quote/PDF status, scoped access token and view reference | Reject invalid selections; return conflict for stale revision; retry same request safely |
| `GET /quotes/:id` | Return generation status and view/download references with scoped token | Pending, failed, expired and missing states are explicit |
| `GET /quotes/:id/pdf` | Serve stored PDF bytes after scoped access validation | Clear recovery if file expired/missing; confirm content headers through real proxy |
| `POST /quotes/:id/prepare-email` | Validated name and scoped token; prepare personalized PDF from original quote snapshot | Return exact PDF version for review, preserving original price/date terms |
| `POST /quotes/:id/email` | PDF version, name/email, explicit confirmation, token and idempotency key | Accepted/failed/unknown status; retries reuse the same dispatch intent |

Generate synchronously if the real deployment comfortably supports the worst approved catalogue/PDF size. If the feasibility test exceeds execution/payload limits, select a durable worker/queue before finalizing the endpoint implementation. Never rely on background promises continuing after a function returns.

Persistence plan:

- `quotes`: immutable selection/content/price snapshot, revision, issue/expiry, generation state, hashed access token, idempotency key and PDF version references.
- `quote_files`: private object key, content hash, anonymous/personalized version, generation result and retention metadata. Email references these stored bytes.
- `email_dispatches`: quote/file version, intended recipient, request fingerprint, idempotency key, state and provider reference. Store only necessary contact data under the chosen retention policy.
- Use database uniqueness/transactions for concurrent duplicate requests. Reusing a request key with different content is a conflict, not a new send.
- Define crash recovery: a retry can resume a pending generation; a file-upload success followed by a database error must not silently produce multiple customer-visible quotes. Clean up orphaned files under the chosen retention process.
- On an email provider timeout after submission, record unknown/pending and reconcile with the provider/idempotency mechanism before resending. Do not report failure as proof that no email was sent.

Private PDFs require application-controlled access. Use private storage and retrieve bytes through the authorized handler; do not assume a public blob URL becomes private because it is hard to guess. Verify proxy handling of PDF headers and download behaviour during the spike. [Vercel private storage](https://vercel.com/docs/vercel-blob/private-storage).

Customer tokens permit access to that quote only; they do not create a public saved-configuration feature. Keep tokens out of logs/referrers where practical and use the selected expiry policy. Apply request size limits, abuse rate limits and allowed-media validation independently of proxy authentication. No account/login requirement for creating or viewing a quotation.

## 6. Frontend implementation sequence

1. Build the mount/unmount integration and local demo shell with visible fixture labeling.
2. Implement typed configuration reducer and derived selectors; calculate dependent compatibility, price and photo state from one selection source.
3. Add Layout and Island with dimensions, no-island rules and secondary dimension imagery.
4. Add Storage selection groups and Carcass cards, descriptions, swatches and price modifiers.
5. Add progress, Back/Continue, invalidation notices and the final summary. Keep actions keyboard-operable and focus predictable.
6. Build responsive gallery, lightbox, loading states and exact/reference/placeholder handling. Scope styles and avoid global CSS resets.
7. Wire File Quotation. Open a loading tab during the user gesture when possible, then navigate it to the authorized PDF; always retain an explicit view/download recovery link. Verify this on actual Safari.
8. Add separate name/email entry, personalized PDF review and confirmation. Send the same reviewed PDF version and expose it for download. Email errors must never remove PDF access.
9. Add optional refresh recovery/analytics/storage-preview switching only after their launch decisions. Step retention is always required.

## 8. Verification and delivery controls

- Shared-domain tests: compatibility groups, invalidation, VAT examples, zero versus absent prices, storage-order-independent keys and complete combination enumeration.
- Integration tests: Shopify adapter pagination/validation, proxy signatures, wrong-shop rejection, stale catalogue, forged prices, persistence failures, PDF access tokens, concurrent duplicate requests and email timeout recovery.
- Browser tests: complete no-email PDF journey; optional reviewed/confirmed email; blocked popup; upstream option changes; failed images/PDF/email with selection retention.
- Manual checks: real Safari/iOS, Android/tablet, visual PDF pagination/content, screenshot comparison to the actual reference and existing-store regression checks. Test runner browser emulation alone does not satisfy all real-device evidence.
- Production gate: zero missing exact photos, all AC01–AC10 pass, service configuration/cost owners recorded, final preview reviewed, approved release and rollback ready.
- Handover: setup commands, app installation/authentication maintenance, environment variable names, catalogue fields/edit workflow, revision/cache refresh, quote/email troubleshooting, retention/cleanup, deployment/rollback and service ownership.
